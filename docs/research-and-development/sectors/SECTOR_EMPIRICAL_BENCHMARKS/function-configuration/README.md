# Configuration faults: controlled implementation case study

Hypothesis: runtime launch declarations and success receipts may diverge from actual callable implementation. Baseline source at BRAINK-BETA-TEST main b00d00924b4dbcf13ca64468aa4790ce3308faf8 had register_module pass, synthetic dispatch completion, ring comparison contrary to its documented hierarchy, unparseable literal backslash-n imports, token-file deploy configuration missing from CLI, and invalid empty package author email. Static AST indexing exposed VFS syntax faults; wheel build exposed metadata failure. These are reproducible source-local implementation findings, not allegations about every owner runtime.

Interventions directly repair each fault without inventing a native KEX engine. Real-call tests count execution and reject duplicate identities, failed executors, invalid output and unmet dependencies. All sixteen ring pairs check the documented ordering. Authenticated loopback HTTP checks denied unauthorized mutation/read/verification, authorized write/read/receipt verification and retained content after reopen. The full source test suite plus VFS tests passed: 25 test cases. A wheel builds and its installed imports/ring smoke check succeeds outside the checkout. Exact test command: .venv/bin/python -m pytest -o addopts='' tests vfs_server/tests. The empty addopts avoids incidental coverage HTML artifacts; no tests were deselected.

Controls: unchanged store implementation and domain layout, explicit fixture callable and local token, no network financial actuation, ephemeral loopback service, separate installation target to avoid source imports masking package omission. The expected authorization denials do not bypass semantic lineage checks: this source does not implement native contextual seed derivation at all.

Critique: 25 passing cases do not establish complete coverage, malicious-host isolation, structural unspoofability or deployment readiness. Ring access is Python logic; descriptors do not allocate physical RAM. Threaded VFS storage and mutable dispatch records require independent concurrency qualification. Original WorkModule input/output specs are not interpreted as enforceable schemas. Successful callable invocation alone does not establish economic or environmental impact. Repairs introduce explicit registration requirements and therefore change callers that relied on silent defaults.

Emergent learning: retaining callable-level evidence alongside launch declarations exposes false operational confidence. An unparseable module and a generated success receipt can coexist in a repository without a full test collection noticing either if only one test directory is configured. Expanded explicit discovery and separately installed smoke checks are essential to this result. Source-local lineage integration must wait for its actual implementation; related service transport configuration cannot be substituted for that semantics.
